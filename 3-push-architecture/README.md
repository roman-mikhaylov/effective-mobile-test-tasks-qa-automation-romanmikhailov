# Задание 3 — архитектура системы push-уведомлений

Здесь описана архитектура системы push-уведомлений для мобильного приложения интернет-магазина «Петрушка Зеленая» (тестовое задание для Effective Mobile, позиция системного аналитика / QA Automation).  

## Кратко про архитектуру

- Вся логика отправки пушей вынесена в отдельный `Notification/Push Service`.  
- Бизнес-сервисы (`Order`, `Cart`, `Campaign`) публикуют доменные события в `Message Queue / Event Bus`.  
- `Notification/Push Service` подписан на эти события, подбирает шаблон, достаёт токены устройств пользователя и отправляет пуши через `Push Provider (FCM/APNS)`. [web:17][web:20]  

Основные контейнеры:

- `API Gateway` — точка входа для мобильного приложения.  
- `User / Order / Cart / Campaign Service` — бизнес-логика пользователей, заказов, корзин, кампаний.  
- `Message Queue / Event Bus` — асинхронный обмен событиями. [web:17]  
- `Notification/Push Service` — формирование и отправка уведомлений, правила частоты/тихих часов, логирование. [web:22]  
- `Device Tokens Storage` — токены устройств.  
- `Template Storage` — шаблоны текстов и payload’ов.  
- `Push Provider (FCM/APNS)` — FCM/APNS. [web:17][web:20]

## Основные сценарии

1. **Изменение статуса заказа**  
   `Order Service` меняет статус, публикует `OrderStatusChanged` → `Notification Service` формирует пуш (шаблон по статусу, номер заказа, сумма) и отправляет через провайдера, приложение открывает экран заказа по deeplink. [web:17]

2. **Брошенная корзина**  
   `Cart Service` публикует `CartCreated/CartUpdated` → воркер в `Notification Service` определяет брошенные корзины по заданным правилам и отправляет напоминания с deeplink на экран корзины. 

3. **Маркетинговая кампания**  
   `Campaign Service` публикует `SendPushToSegment` → `Notification Service` разворачивает сегмент в пользователей, применяет ограничения по частоте и «тихим часам» и отправляет кампанийные пуши.

Подробное текстовое описание — в `docs/03-architecture-push.md`.

## Как я бы объяснил это на собеседовании

> Я вынес работу с push-уведомлениями в отдельный Notification/Push Service и связал его с бизнес-сервисами через шину доменных событий. Order, Cart и Campaign сервисы публикуют события вроде `OrderStatusChanged`, `CartUpdated`, `SendPushToSegment` в Event Bus, а push-сервис подписан на них, выбирает шаблон, достаёт токены устройств и отправляет пуши через FCM/APNS. Это даёт слабую связанность и асинхронность: бизнес-логика не зависит от конкретного провайдера, а изменения заказов или корзин не блокируются отправкой уведомлений. В Notification Service сосредоточены шаблоны, пользовательские настройки, правила частоты и тихих часов, логирование и ретраи, поэтому новые типы уведомлений добавляются за счёт новых доменных событий и шаблонов, практически без изменений остальной системы.
